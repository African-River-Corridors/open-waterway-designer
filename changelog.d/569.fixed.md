- **A pool lattice line that crosses itself is never spliced, and an option whose line still crosses itself fails a named check.** The pool lattice could return a line that loops inside one pool: water below the grade costs nothing to cut, so length in the water is free, and a search state (position, heading, turn) has no memory of the path already laid. On a strongly meandering river with nested lobes the least-cost line then ran far past where the river turns back and crossed its own track, and that line was spliced into the design line while the option passed. Now a pool (or a piece of a long pool) whose own line crosses itself is searched again with its end moved along the baseline, as for a pool that cannot close (downstream first, then upstream, in steps of a quarter of R_min); if no end gives a simple line, the pool keeps the baseline with the reason "its line crosses itself, even with the end moved". After the pools are joined, a pool whose line crosses the rest of the design line keeps the baseline too (the later pool at each crossing), until the line is simple. Each such pool gets a sanity warning. As a backstop, the lattice option carries the check `no_self_crossing` (`ok`, `first_crossing_m`): a line that still crosses itself fails it like `R_min`, `owd optimise` prints "FAILS no_self_crossing" and "marked failed", and `--strict` exits 1. On the synthetic meander of the issue (heading 110 degrees x sin(2 pi s / 2,000 m), R_min 340 m) the search for the pool from 0 to 3,500 m returns 4.8 km of line that crosses itself twice; with the weir at 3,720 m the pool now closes on an end moved 85 m downstream with a simple line. The search itself still finds looped lines; only the guard keeps them out of the design (issue #569).
